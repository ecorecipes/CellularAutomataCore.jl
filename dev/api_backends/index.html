Backends

The engines that advance a problem, and the interface for writing one.

Backends

CellularAutomataCore.AbstractBackend — Type
AbstractBackend

Supertype of backends, which say where the state lives and how cells are visited: ReferenceBackend, ArrayBackend, SparseBackend, GPUBackend, AgentsBackend and ArkBackend. Every backend gives exactly the same result for the same problem, including stochastic rules (see uniform).

A new backend implements supports, CellularAutomataCore.check_problem, CellularAutomataCore.allocate_state, CellularAutomataCore.advance!, CellularAutomataCore.current_state, CellularAutomataCore.set_state!, read_cell and write_cell! for its type.

Plots.jl exports a different AbstractBackend; with both packages loaded, write CellularAutomataCore.AbstractBackend or import it explicitly.

CellularAutomataCore.ArrayBackend — Type
ArrayBackend(; threaded=Threads.nthreads() > 1)

Dense arrays on the CPU. On a lattice the state is padded with a halo as wide as the widest neighbourhood or kernel field, refreshed from the boundary conditions once per sweep, so the inner loop does no boundary arithmetic; with threaded=true the lattice is split into slabs along its last axis, one task per slab. The result does not depend on the thread count. Runs every scheme.

source
CellularAutomataCore.SparseBackend — Type
SparseBackend(background; tilesize=32, threaded=Threads.nthreads() > 1)

Store and update only the parts of a lattice that differ from the background state (for example 0, :S or a layered NamedTuple). The lattice is cut into tilesize-wide square tiles; each step updates the stored tiles and their neighbours within reach of the neighbourhood, and drops tiles that end up entirely background. The cost per step is proportional to the active area, not to the size of the lattice.

The rule must be quiescent: a background cell whose neighbours are all background must stay background, at every cell and time. Rules with spontaneous events (a lightning strike in an empty forest) are not, and are rejected when the problem is set up if a sample of cells shows it. Runs Synchronous and Stochastic on lattices without kernel fields; masks and covariates are supported.

source
CellularAutomataCore.GPUBackend — Type
GPUBackend(device; workgroupsize=256)
GPUBackend(array)

Run on a GPU (or any other KernelAbstractions.jl device) with one kernel per sweep. device is a KernelAbstractions backend such as CUDABackend(), ROCBackend(), MetalBackend(), JLBackend() (JLArrays, for testing without a GPU) or KernelAbstractions.CPU(); the second form takes it from an array of the device's type (via KernelAbstractions.get_backend). Needs using KernelAbstractions. The initial state, covariates and mask are copied to the device; rules, parameters and kernel-field sources must be usable inside a kernel (isbits values, no allocation). Runs Synchronous, Stochastic and Checkerboard on lattices.

Apple GPUs (using Metal; GPUBackend(MetalBackend())) have no double precision: write rules with Float32 parameters and literals (0.5f0), so that bernoulli draws in single precision, and use Stochastic(0.5f0), KernelField(...; precision=Float32) and Lenia(; precision=Float32). Integer and Boolean models then agree with the CPU backends exactly; models that call transcendental functions on floating-point states (Lenia) agree to rounding, because GPU implementations of exp and fused multiply-adds differ in the last bits.

CellularAutomataCore.ReferenceBackend — Type
ReferenceBackend()

The slow, simple backend that the others are tested against: it applies the boundary conditions on every neighbour access and visits cells serially.

Agent backends

Hybrid models: the state lives in an Agents.jl model or an Ark.jl world shared with mobile agents.

CellularAutomataCore.AgentsBackend — Type
AgentsBackend(mode=:grid; agent_type=nothing, init! = nothing, agent_step! = nothing,
              model_step! = nothing, threaded=Threads.nthreads() > 1)

Keep the state in an Agents.jl model (StandardABM), so that mobile agents can read and change the cells. Needs using Agents.

  • mode = :grid: the state is an array in the model's properties.
  • mode = :cells: every cell is an agent with fields id, pos (on a lattice) and state; the agent with id i is the cell with linear index i, so model[i].state is its state. Mobile agents get ids after the cells. The cell agents occupy every position, so Agents.jl functions that look for empty positions find none (pass ifempty=false to randomwalk!), and nearby_agents returns cells as well as mobile agents.

The model's space is a GridSpace of the lattice's size, periodic along the axes whose boundary is Periodic (no space on a GraphSpace). Its properties give the parameters as model.p and the time as model.t, and abmrng(model) is seeded from the problem's seed.

Mobile agents are of type agent_type (an @agent type for the space). init!(model) adds them once the cells are set, at the start of a run and on reinit!. Each step runs the cellular automaton's sweep, then agent_step!(agent, model) for every mobile agent in order of id, then model_step!(model). Inside them, read_cell(model, pos) and write_cell!(model, pos, v) read and change a cell. From a callback, agent_model(integ) returns the model.

Without mobile agents the result equals that of ArrayBackend exactly. Runs every discrete-time scheme; the sweep uses ArrayBackend(; threaded).

source
CellularAutomataCore.ArkBackend — Type
ArkBackend(mode=:grid; components=(), init! = nothing, update! = nothing,
           threaded=Threads.nthreads() > 1)

Keep the state in an Ark.jl World (an entity component system), so that mobile agents, which are entities, can read and change the cells. Needs using Ark.

  • mode = :grid: the state is an array in a world resource.
  • mode = :cells: every cell is an entity with a CACell component holding its linear index and state, which queries can select: Query(world, (CACell{T},)) for cell type T.

components lists the component types of the mobile agents, which the world must know when it is created. init!(world, p) creates the agents once the cells are set, at the start of a run and on reinit!. Each step runs the cellular automaton's sweep, then update!(world, p, t) with the parameters and the new time. Inside them, read_cell(world, I) and write_cell!(world, I, v) read and change a cell, and get_resource(world, Xoshiro) is a random number generator seeded from the problem's seed. From a callback, agent_model(integ) returns the world.

Without mobile agents the result equals that of ArrayBackend exactly. Runs every discrete-time scheme; the sweep uses ArrayBackend(; threaded).

source
CellularAutomataCore.CACell — Type
CACell{S}(index, state)

The component of a cell entity in ArkBackend(:cells): the cell's linear index (its vertex on a GraphSpace) and its state, of the type a cell has in the problem (a NamedTuple for a layered state).

source
CellularAutomataCore.agent_model — Function
agent_model(integ::CAIntegrator)

The Agents.jl model or the Ark.jl world that holds the state of an integrator solved with AgentsBackend or ArkBackend, for callbacks that add, inspect or remove mobile agents. Changes made through it are seen by integ.u afterwards, and changes made to integ.u before the call are kept.

source
CellularAutomataCore.read_cell — Function
read_cell(model, I)
read_cell(backend, state, I)

The state of the cell at I (a CartesianIndex, a tuple such as an agent's pos, or a linear index; a vertex on a GraphSpace). The first form reads from the Agents.jl model or Ark.jl world of AgentsBackend or ArkBackend, for mobile agents; the second is part of the interface every backend implements.

CellularAutomataCore.write_cell! — Function
write_cell!(model, I, v)
write_cell!(backend, state, I, v)

Set the cell at I to v, converted to the state's cell type; the forms are those of read_cell.

Writing a backend

A backend is a subtype of AbstractBackend with methods of supports, read_cell, write_cell! and the functions below, which are public but not exported. A backend that runs its own engine can evaluate the rule at a cell with CellularAutomataCore.update_cell.

CellularAutomataCore.check_problem — Function
CellularAutomataCore.check_problem(backend, prob, scheme)

Raise an error, when a problem is set up, if backend cannot run prob with scheme (for example a space or kernel field it does not handle); return nothing otherwise. Part of the backend interface; the fallback accepts every problem.

source
CellularAutomataCore.allocate_state — Function
CellularAutomataCore.allocate_state(backend, prob, scheme) -> state

Create the backend's state for a run of prob with scheme, holding the initial state prob.u0 and any buffers. Called once per integrator, after supports and CellularAutomataCore.check_problem. Part of the backend interface, with CellularAutomataCore.advance!, CellularAutomataCore.current_state, CellularAutomataCore.set_state!, read_cell and write_cell!. A backend implements them for its own type, the type of its state and the schemes it supports.

source
CellularAutomataCore.advance! — Function
CellularAutomataCore.advance!(backend, state, prob, scheme, p, t)

Advance state by one step of scheme, from time t to t + 1, with parameters p (the integrator's, which a callback may have changed from prob.p). Stochastic rules draw their random numbers from the time, the cell and the seed (see uniform), so the order in which a backend visits the cells does not change the result. Part of the backend interface.

source
CellularAutomataCore.current_state — Function
CellularAutomataCore.current_state(backend, state) -> u

A copy of the current state in the layout of prob.u0 (an array the size of the space, or a NamedTuple of them), which the integrator may keep. Part of the backend interface.

source
CellularAutomataCore.set_state! — Function
CellularAutomataCore.set_state!(backend, state, u)

Replace the whole current state with u, given in the layout of prob.u0. Used by reinit! and to apply changes callbacks make to integ.u. Part of the backend interface.

source
CellularAutomataCore.update_cell — Function
CellularAutomataCore.update_cell(prob, u, I, t, p=prob.p)

The new state of cell I when the whole state u (in the layout of prob.u0) is updated synchronously at time t with parameters p, without changing u: the rule applied to the cell and its neighbours, read with the boundary conditions of the space, with the covariates of the problem and the same random numbers as every backend. A masked cell keeps its state. I is a CartesianIndex, a tuple or a linear index on a lattice, and a vertex on a GraphSpace.

A building block for backends that run their own engine. Problems with kernel fields, BlockRules and EventRules are not supported.
