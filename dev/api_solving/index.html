Solving

Problems, integrators, solutions, callbacks, ensembles and update schemes.

Problems, integrators and solutions

The interface follows SciML: CAProblem(rule, u0, tspan, p), solve(prob, alg; saveat, callback, ...), init/step!/solve!, integrators with u, t and p, and SciMLBase's remake, reinit!, terminate!, u_modified!, NullParameters, ReturnCode, DiscreteCallback, CallbackSet, EnsembleProblem, EnsembleThreads, EnsembleSerial and EnsembleDistributed, re-exported by this package. The update scheme is the algorithm.

CellularAutomataCore.CAProblem — Type
CAProblem(rule, u0, tspan, p=NullParameters(); space=nothing, seed=0,
          covariates=(;), fields=(;), mask=nothing, kwargs...)

A cellular-automaton problem, in the style of SciML problems: rule applied to the initial state u0 over tspan (a number of steps n, meaning (0, n), or a tuple (t0, t1) of integer times; real times for an EventRule solved in continuous time with Gillespie) with parameters p, which rules read as ctx.p.

  • space: an AbstractSpace; by default a Torus of the size of u0.
  • seed: the seed of the counter-based random numbers (uniform).
  • covariates: a NamedTuple of arrays the size of the space, or with one more (time) axis, read with covariate.
  • fields: a NamedTuple of KernelFields, read with field; merged with the rule's own fields.
  • mask: an array of Bools the size of the space; cells where it is false never update (no-data cells, water, roads), though their neighbours still read them.
  • kwargs: solver keywords stored with the problem, as SciML problems store them (callback, saveat, save_everystep, save_start, save_end, backend; see init). solve and init use them unless given the same keyword, except that callbacks from both are combined, the problem's first.

u0 is an array the size of the space, or a NamedTuple of such arrays (one per layer). The problem checks, once, that everything fits the space (StateShapeError, IncompatibleSpaceError) and that the rule can read every value of u0 (InvalidStateError). Change a problem with remake.

SciMLBase.remake — Method
remake(prob::CAProblem; rule, u0, tspan, p, space, seed, covariates, fields, mask,
       kwargs)

A copy of prob with some of its parts replaced (SciMLBase's remake): for example remake(prob; seed=2) for another replicate, or remake(prob; p=(β=0.4,)) for other parameters. kwargs replaces the stored solver keywords as a whole.

CommonSolve.init — Method
init(prob::CAProblem, alg=Synchronous(); backend=ArrayBackend(), saveat=nothing,
     save_everystep=saveat === nothing, save_start=true, save_end=true,
     callback=nothing)

Set up a problem for stepping, with SciML's saving and callback keywords:

  • saveat: an integer k (save every k steps) or a collection of times; without it every step is saved unless save_everystep=false. The start and end states are saved unless save_start/save_end are false.
  • callback: a DiscreteCallback, a CallbackSet, or a collection of them, checked in order after every step (PeriodicCallback, PresetTimeCallback and SavingCallback build common ones).
  • backend: the AbstractBackend.

Solver keywords stored in the problem apply unless given here; callbacks from both are combined, the problem's first.

Raises UnsupportedCombinationError if the backend cannot run the scheme.

CommonSolve.solve — Method
solve(prob::CAProblem, alg=Synchronous(); backend=ArrayBackend(), saveat=nothing,
      save_everystep=saveat === nothing, save_start=true, save_end=true,
      callback=nothing) -> CASolution

Run a problem to the end of its tspan; the keywords are those of init. Ensembles use SciMLBase's EnsembleProblem, whose default prob_func here gives each trajectory its own seed (seed_trajectory); a prob_func of your own receives the problem and SciMLBase's EnsembleContext, as in (prob, ctx) -> remake(prob; seed=ctx.sim_id).

julia> sol = solve(CAProblem(Life(), zeros(Int8, 8, 8), 10); saveat=5);

julia> sol.t
3-element Vector{Int64}:
  0
  5
 10

CellularAutomataCore.CAIntegrator — Type
CAIntegrator

The stepping state of a problem, created by init(prob, alg; ...), with the interface of a SciML integrator:

  • integ.u: the current state, in the layout of u0. Inside a callback's affect!, change it in place and the change is applied; elsewhere, call u_modified!(integ, true) after changing it.
  • integ.t: the current time; integ.p: the parameters, which may be reassigned (integ.p = ...) to change rates from the next step on.
  • step!(integ), step!(integ, n), solve!(integ), reinit!(integ), terminate!(integ). In continuous time (Gillespie) a step is one event, or a stop at a time given to add_tstop!.
source
SciMLBase.u_modified! — Method
u_modified!(integ::CAIntegrator, modified::Bool)

Tell the integrator whether integ.u was changed, so that the change is (or is not) applied before the next step. Callbacks set it automatically.

SciMLBase.terminate! — Method
terminate!(integ::CAIntegrator, retcode=ReturnCode.Terminated)

Stop the run after the current step, for example from a callback when an epidemic dies out; the solution's retcode records it.

source
SciMLBase.reinit! — Method
reinit!(integ::CAIntegrator, u0=integ.prob.u0; t0=integ.prob.tspan[1])

Restart an integrator from u0 at time t0, discarding its saved states and rerunning the callbacks' initialize. The random numbers restart too, so reinitialising with the same u0 and t0 replays the run.

source
SciMLBase.add_tstop! — Method
add_tstop!(integ::CAIntegrator, t)

For a continuous-time (Gillespie) integrator, make the run stop at time t even if no event happens then, so that callbacks can act at exactly t (PresetTimeCallback and PeriodicCallback do this). For discrete schemes every whole time is already a stop, and it does nothing.

source
CellularAutomataCore.CASolution — Type
CASolution

The result of solve, with the fields of a SciML solution: the saved states sol.u at times sol.t, sol.prob, sol.alg (the update scheme), sol.retcode (ReturnCode.Success, or ReturnCode.Terminated after terminate!) and sol.backend. Times are integers, or Float64 in continuous time (Gillespie). sol(t) is the state saved at time t and sol[i] is sol.u[i]; final_state and trajectory are conveniences.

source
CellularAutomataCore.final_state — Function
final_state(sol)

The last saved state of a solution.

source
CellularAutomataCore.trajectory — Function
trajectory(sol)

The saved states stacked into one array with time as the last axis: an n-dimensional state gives an (n + 1)-dimensional array. For a layered state, a NamedTuple with one such array per layer.

Callbacks

CellularAutomataCore.PeriodicCallback — Function
PeriodicCallback(affect!, Δt; initial_affect=false, phase=0)

A DiscreteCallback running affect!(integ) after every step that brings the time to t0 + phase + k Δt (k ≥ 1), and also at the start if initial_affect; as in DiffEqCallbacks.jl. In continuous time (Gillespie) Δt and phase may be real, and the run stops at exactly those times.

source
CellularAutomataCore.PresetTimeCallback — Function
PresetTimeCallback(tstops, affect!)

A DiscreteCallback running affect!(integ) after the steps that bring the time to one of tstops; as in DiffEqCallbacks.jl. In continuous time (Gillespie) the run stops at exactly those times.

source
CellularAutomataCore.SavingCallback — Function
SavingCallback(save_func, saved_values::SavedValues; saveat=nothing, save_start=true)

A DiscreteCallback that pushes save_func(u, t, integ) into saved_values at the start and after every step (or every saveat steps, or at the times in saveat): a cheap way to record a summary, such as the number of infected cells, without saving whole states. As in DiffEqCallbacks.jl.

source
CellularAutomataCore.SavedValues — Type
SavedValues(tType, sType)

Storage for SavingCallback: times t::Vector{tType} and values saveval::Vector{sType}; as in DiffEqCallbacks.jl.

Ensembles

SciMLBase.EnsembleProblem — Method
EnsembleProblem(prob::CAProblem; prob_func=seed_trajectory, kwargs...)

SciMLBase's EnsembleProblem, with a default prob_func that gives each trajectory its own seed (seed_trajectory). Solve it with solve(eprob, alg, EnsembleThreads(); trajectories=n, backend=...); the prob_func(prob, ctx) and output_func(sol, ctx) functions receive SciMLBase's EnsembleContext (ctx.sim_id, ctx.sim_seed).

source
CellularAutomataCore.seed_trajectory — Function
seed_trajectory(prob, ctx)

The default prob_func of an EnsembleProblem built on a CAProblem: trajectory i is remake(prob; seed=prob.seed + i), or uses the per-trajectory seed SciMLBase derives when the ensemble is solved with a seed keyword. Without it every trajectory would repeat the same counter-based random numbers.

Update schemes

CellularAutomataCore.AbstractScheme — Type
AbstractScheme

Supertype of update schemes, the algorithms passed to solve (a subtype of SciMLBase's AbstractSciMLAlgorithm): Synchronous, Stochastic, Checkerboard, RandomSequential, Margolus and, in continuous time, Gillespie.

source
CellularAutomataCore.Synchronous — Type
Synchronous()

Every cell computes its next state from the current states of its neighbours, then all cells update at once (double buffering).

source
CellularAutomataCore.Stochastic — Type
Stochastic(p)

A synchronous step in which each cell updates with probability p and otherwise keeps its state: an asynchronous scheme that still runs in parallel. Whether a cell updates is decided by its draw k = 0 (uniform), so it is reproducible on every backend; the draw has the precision of p, so Stochastic(0.5f0) needs no double precision.

source
CellularAutomataCore.Checkerboard — Type
Checkerboard()

Two synchronous half-steps per step on a lattice: first the cells whose indices sum to an even number, then the others, each half reading the state left by the previous one. On a square lattice with a von Neumann neighbourhood the cells updated together are never neighbours. Kernel fields are computed once, at the start of the step.

source
CellularAutomataCore.RandomSequential — Type
RandomSequential()

Cells update one at a time, in a fresh random order every step, each reading the current (partly updated) state: the classic asynchronous scheme. The order is drawn from the problem's seed, so runs are reproducible. Kernel fields are computed once, at the start of the step. Sequential by nature, so it runs on the CPU backends only.

source
CellularAutomataCore.Margolus — Type
Margolus()

The Margolus neighbourhood scheme for BlockRules: the lattice is cut into 2 × 2 blocks, each block is replaced by the rule's function of it, and the partition shifts by one cell diagonally between even and odd steps. Needs a two-dimensional periodic lattice with even side lengths.

source
CellularAutomataCore.Gillespie — Type
Gillespie(method=:next_reaction)

Exact, event-by-event simulation of an EventRule in continuous time (the stochastic simulation algorithm), on the CPU backends (ArrayBackend, ReferenceBackend). Time is real: tspan may be (0.0, 12.5), saveat takes real times, step! advances one event, and the solution's t is a Vector{Float64}.

  • :next_reaction: each cell has its own exponential clock, kept in an indexed heap; after an event only the cell and the cells whose neighbourhoods contain it are recomputed (the modified next-reaction method, with Gibson–Bruck reuse of waiting times). The cost of an event does not grow with the lattice.
  • :direct: the direct method, summing all rates at every event; slow, kept as a reference.
  • :composition_rejection: the direct method with composition–rejection selection (Slepoy et al., 2008): cells are grouped by the binary order of magnitude of their rates, an event picks a group by its total rate and then a member by rejection, so its cost does not grow with the lattice either.

Random numbers are counter-based, as everywhere in the package: the next-reaction method draws cell i's n-th waiting time from (seed, i, n), so runs are reproducible. The methods sample the same process but consume draws differently, so they agree in distribution, not path by path.

Rates are recomputed when a callback changes the state or integ.p, and at every whole time when a covariate has a time axis (the rule sees ctx.t, the integer part of the time). KernelFields are kept up to date event by event: when a cell changes, the cells that read it gain its weighted change and their rates are recomputed, so an event costs time in proportion to the kernel's size; the fields are recomputed from the state after every n events on n cells, so rounding does not accumulate.
